# Requirements specification

This repository is the pipeline itself: a web application that turns a task described in conversation into requirements, an API design and verified, published code in a GitHub repository. This contract describes its HTTP API, served by the backend in `backend/`; the contract tests in `contract-tests/` exercise it over HTTP.

Endpoints that need Temporal, an LLM provider or GitHub answer 503 or a GitHub error when those are not reachable, as they are not in the self-contained service image the contract tests run against.

Errors carry a `detail` string, except FastAPI's own request validation, which answers 422 with a list of the problems found in `detail`.

## Functional requirements

| ID | Requirement | Description | Priority | Rationale |
| --- | --- | --- | --- | --- |
| FR-1 | Register the first account | While no account exists, anyone can register one with a login and a password and is signed in as its administrator. Once any account exists, registration is closed and answers 403. GET /auth/registration tells whether it is still open. | Must | The first user sets up the instance without an operator. |
| FR-2 | Sign in | A user signs in with login and password and receives a bearer token, which is also set as an HttpOnly, SameSite=Strict session cookie. An unknown login or a wrong password answers 401 without saying which. Logins are compared case-insensitively and surrounding whitespace is ignored. | Must |  |
| FR-4 | Current user | GET /auth/me returns the signed-in user's login, when the session expires and whether the user is the administrator. | Must |  |
| FR-5 | Sign out | POST /auth/logout clears the session cookie and answers 204, signed in or not. | Must |  |
| FR-6 | Administer accounts | Only the first user, the administrator, lists accounts (login and creation time) and creates new ones; any other user receives 403. Creating a login that already exists answers 409. | Must |  |
| FR-7 | Validate account details | A login is an email address or a username of letters, digits and . _ % + -, 3 to 254 characters. A password has 8 to 1024 characters. Anything else answers 422 when an account is created. | Must |  |
| FR-9 | Browse repositories | Signed-in users list the repositories the GitHub App installation can access and the branches of one of them, a page at a time with the number of the next page. | Must |  |
| FR-10 | Specify a task in a requirements session | A requirements session starts in a chosen repository and branch from the intake: the kind of task (new service, API change, bugfix or documentation), the answers to that kind's questions and what needs to be done. An LLM interviewer then records requirements while the user sends messages or answers its questions. A failed turn can be retried, and a session can be forked after any message. | Must |  |
| FR-11 | Requirements intake | GET /requirements/intake returns the kind question, the kinds of task, the questions asked for each kind and the task question, for the page to show before a session starts. | Must |  |
| FR-12 | Finalize requirements | Finalizing a session writes its requirements document, available for download once ready. A task on an existing service (API change, bugfix or documentation) is specified against the contract the repository holds in contracts/; a repository without a readable contract cannot be finalized for one. | Must |  |
| FR-13 | Design the API | A new service or an API change continues in an API design session started from its completed requirements session. Its conversation records the endpoints, schemas and implementation language, and finalizing it renders the OpenAPI document. | Must |  |
| FR-14 | Deliver the task | A finalized task is delivered: code is generated or changed, the service and its contract tests are written by separate coding agents, and verification runs the tests against the built service, repairing the failing side a bounded number of times. A bugfix's new tests must first fail against the service as the repository holds it. The session shows the delivery's progress, its agents' questions can be answered, and a failed stage can be retried. | Must |  |
| FR-15 | Publish verified work | Only a delivery that passed verification is pushed, with the repository's updated contract and contract tests, to a new branch of the session's repository. A documentation change, which has no check yet, is pushed and marked as unverified. | Must |  |
| FR-16 | Chat with the LLM | A user sends a free-form request, optionally with one attached file and a repository to work in, follows it up, retries a failed answer or forks the conversation after one of their messages. Attachments and generated documents can be downloaded. | Must |  |
| FR-17 | List workflow executions | Signed-in users list the workflow executions of the namespace, newest first, 50 per page, optionally of one workflow type, continuing with the returned page token. | Should |  |
| FR-18 | Start the sample workflow | POST /start runs the sample greeting workflow and returns its result. | Could |  |
| FR-19 | Update a session's checkout | While a requirements session waits for the user, its branch can be checked out again at its latest commit, which the interview reads and the task is finalized against from then on, such as a commit that added the contract the task needs. The session shows the commit it is checked out at. A failed update keeps the earlier checkout and says so. | Must |  |
| FR-20 | Code review step after successful verification | The delivery pipeline runs a code review step only once both the implementation and the tests exist and verification has shown that they pass against each other. | Must | User asked for a review step that runs after implementation and tests are ready and verified against each other. |
| FR-21 | Review covers only the delivery's changes | The code review step examines only the changes made by the current delivery and reports no findings about code that the delivery did not change. | Must | User: the step should verify the changes, and only them. |
| FR-22 | Review targets issues the tests do not cover | The code review step looks for potential issues in the changes that the passing test suite does not cover. | Must | User: verify the changes for potential issues not covered by tests. |
| FR-23 | Reviewer told not every observation is worth reporting | The reviewing LLM's instructions state that not every observation is worth reporting, so that it reports only findings significant enough to need a correction. | Must | User: the LLM should know that not everything is worth mentioning. |
| FR-24 | Review findings passed to the next repair cycle | When the code review step reports findings, they are passed as input to the next repair cycle. | Must | User: findings should be passed to the next cycle. |
| FR-25 | Findings decide which worker runs | Whether the next cycle runs the implementation worker, the test generation worker, or both is decided by the nature of the review findings. | Must | User: whether the implementation or testing worker runs depends on the nature of the findings. |
| FR-27 | Verify and review again after fixing findings | After a round that corrects review findings, the pipeline runs verification again and, once verification passes, runs the code review step again. | Must | User chose: verify again, then review again. |
| FR-28 | Separate limit of 5 review rounds | The number of review-driven correction rounds is capped at 5 by a limit of its own, separate from the existing limit of 5 test repair rounds, and review rounds do not use up test repair rounds. | Must | User chose a separate limit of review rounds, set to 5 like test repairs. |
| FR-29 | Push as unverified when review findings remain | When review findings remain after the review round limit is reached and the tests pass, the delivery is still pushed to the repository, marked as unverified, and a flag that asks a human for attention is raised in the delivery progress. | Must | User: push as unverified, raise a flag to the human. |
| FR-30 | Human decides on open review findings | When the open-findings flag is raised, the user can either accept the delivery as it is, which clears the flag, or give instructions on what to do about the findings. | Must | User: ability to tell what to do or accept as is. |
| FR-31 | Human instructions start a new fix round on the same branch | When the user gives instructions about open review findings, the instructions are passed to a new round of fixes, followed by verification and code review, and the result is pushed to the same branch as the unverified delivery. | Must | User chose: instructions go into a new round of fixes, then verification, review and push to the same branch. |
| FR-32 | Open review findings recorded in the commit message | When a delivery is pushed with open review findings, the commit message of the pushed commit lists those findings. | Must | User: findings should also be visible in the pushed branch, in the commit message. |
| FR-33 | Review findings shown in delivery progress | For every code review round, the delivery progress shows the findings reported and, for each finding, the worker it was sent to (implementation, test generation, or both). | Must | User confirmed: show findings for every review round, with the worker each was sent to. |
| FR-34 | Open a pull request after the push | After a delivery's branch has been pushed, the workflow opens a pull request from that branch to the repository's default branch, and the pull request's description says what the delivery changed. | Must | User: at the end of the workflow, after code is pushed, create a PR to the default branch with a description of what changed. |
| FR-35 | Pull request for every pushed delivery | A pull request is opened for every pushed delivery, including unverified ones: documentation changes and deliveries pushed with open review findings. | Must | User chose: every pushed delivery, including unverified ones. |
| FR-36 | Missing pull request permission does not fail the push | When the pull request cannot be opened because the GitHub App installation lacks the pull request permission, the pushed branch remains, the delivery does not fail, and the delivery progress reports that the permission is missing. | Must | User chose: report it in the delivery progress without failing the push. |
| FR-37 | Update the existing pull request on a later push | When a later push goes to a branch that already has an open pull request (after the user's instructions on open review findings), no new pull request is opened; the existing pull request is kept and its description is updated to say what the delivery changed. | Must | User chose: keep the existing pull request and update its description. |
| FR-38 | Unverified deliveries open draft pull requests | A pull request for an unverified delivery is opened as a draft, and when the delivery has open review findings, the pull request's description lists them. | Must | User chose: draft pull request with the open findings in the description. |
| FR-39 | Pull request link in delivery progress | Once the pull request is opened, the delivery progress shows a link to it. | Must | User chose: show the pull request link once it is opened. |
| FR-40 | Mention the app to request a fix | When a comment on a pull request mentions the GitHub App and asks for a fix, the comment's text is passed to a new round of fixes, followed by verification and code review, and the result is pushed to the pull request's branch, as with the user's instructions on open review findings. | Must | User: mention the app in the PR asking for a fix; behave like instructions on open findings. |
| FR-41 | Mention the app to ask for clarification | When a comment on a pull request mentions the GitHub App and asks for clarification, the app replies in the pull request with an LLM-generated answer based on the delivery's sessions and code. | Must | User chose an LLM reply in the PR based on the delivery's session and code. |
| FR-42 | Act only on authorised mentions on the app's PRs | The app acts on a mention only when it is on a pull request the app opened for a delivery and its author has write access to the repository; any other mention is ignored. | Must | User chose: only PRs the app opened, from users with write access. |
| FR-43 | Require a signed-in user | Every endpoint other than sign-in, registration, its status, sign-out and POST /connectors/github/events requires a valid, unexpired token, sent as a bearer token or the session cookie, and answers 401 with WWW-Authenticate: Bearer otherwise. | Must | Replaces FR-3: GitHub must be able to deliver webhook events without a user token. |
| FR-44 | Receive GitHub webhook events | POST /connectors/github/events accepts a GitHub webhook delivery only when its X-Hub-Signature-256 signature matches the connected app's webhook secret, and rejects any unsigned or wrongly signed delivery without acting on it. | Must | User chose a signed webhook endpoint to receive mentions. |
| FR-45 | Mentions in conversation and inline review comments | A mention of the app counts in both pull request conversation comments and inline review comments. | Must | User chose conversation and inline review comments. |
| FR-46 | Classify a mention as fix or clarification | An LLM classifies each authorised mention as a fix request or a request for clarification; when it cannot tell, the app replies in the pull request asking which one is meant and takes no other action. | Must | User chose LLM classification with a reply when unsure. |
| FR-47 | Queue fix requests during a running round | When a fix is requested by a mention while a fix round for the same delivery is running, the request is queued and its round starts after the current round ends, in the order the requests arrived. | Must | User chose to queue requests that arrive during a running round. |
| FR-48 | Acknowledge fix requests in the pull request | When a fix round requested by a mention starts, the app replies in the pull request that it has started, and when the round ends it replies again with the outcome: that the result was pushed, or what failed. | Must | User chose a reply when the round starts and another with the outcome. |
| FR-49 | Optional webhook secret for a manual connection | A GitHub App connection created from an app ID and private key accepts an optional webhook secret, stored encrypted and never returned; while a connection has no webhook secret, POST /connectors/github/events rejects every delivery and mentions are not handled. | Must | User chose an optional webhook secret entered with the app ID and key. |
| FR-50 | Connect GitHub | All users share one GitHub App connection. It is created from an app ID, its PEM private key, optionally the account it is installed on and optionally a webhook secret, or from the code GitHub returns after creating an app from this instance's manifest. It can be checked against GitHub and removed. Its status shows whether it is configured, whether the key can be encrypted, the app, the installation, when it was last validated and whether a webhook secret is set. | Must | Replaces FR-8: the user confirmed a manual connection takes an optional webhook secret and the status shows whether one is set. |
| FR-51 | Mentions shown in delivery progress | The delivery progress shows each authorised mention on the delivery's pull request, how it was classified (fix, clarification or unclear) and the fix round or reply it led to. | Must | User chose to show each mention, its classification and the round or reply it led to. |
| FR-52 | Meaningful pull request title and description | The title and description of the pull request opened or updated at the end of a delivery are written by an LLM from the task, its requirements and the delivery's code diff: the description says what the delivery changed and the purpose of the change, and the title names the specific change instead of a fixed phrase for the task kind. | Must | User: PR descriptions and titles should describe what changed and why; chose an LLM writing them from the task, requirements and diff. |
| FR-53 | Summary replaces the current description sections | The pull request description consists of the LLM-written summary, followed only by the list of open review findings when the delivery has any; it no longer contains the requirement list, the verification status section or the branch and commit details it contains today. | Must | User chose to replace everything with the new summary, but to keep listing open findings below it (FR-38 stays). |
| FR-54 | Fall back to the generic title and description | When the LLM cannot write the pull request title or description (for example, it is unavailable), the pull request is opened or updated with today's generic title and description, and the delivery does not fail. | Must | User chose a fallback that keeps the delivery from failing. |
| FR-55 | Unverified marker in the pull request title | The title of a pull request for an unverified delivery carries an "(unverified)" marker in addition to the LLM-written title, as today's generic title does. | Must | User chose to keep the "(unverified)" marker in the title of draft pull requests. |
| FR-56 | Start onboarding from a repository and branch | A signed-in user can start onboarding an existing repository as its own action on a chosen repository and branch, outside requirements sessions and the requirements intake. | Must | User chose a separate action on a repository/branch. |
| FR-57 | Onboarding produces the full contract, tests and Dockerfile | Onboarding produces for the repository the full contract in contracts/ (requirements.json, requirements.md, api.json, openapi.yaml, language.json), contract tests and a root Dockerfile, and the contract tests are verified to pass against the existing code built with that Dockerfile. | Must | User chose the full contract plus contract tests and Dockerfile, all verified against the existing code. |
| FR-58 | LLM drafts the contract, user reviews it | An LLM drafts the requirements and the API from the repository's existing code, and the user reviews and corrects the drafts in an interview before the onboarding is finalized. | Must | User chose LLM drafting followed by user review in an interview. |
| FR-59 | Repair tests, or code only when the user confirms a bug | When a contract test fails against the existing code during onboarding, the repair changes the tests (and the drafted contract); the existing code is changed only after the user confirms that the failure reveals a bug in it. | Must | User chose: the tests, or the code if the user confirms it is a bug. |
| FR-60 | Publish onboarding like a delivery | The onboarding result goes through the code review step and is pushed to a new branch with a pull request to the repository's default branch, in the same way as a delivery. | Must | User chose: new branch and pull request like a delivery, including code review. |
| FR-61 | Warn before replacing an existing contract | When the chosen branch already has a contract in contracts/, the user is warned before onboarding proceeds and chooses whether to replace it; if the user declines, the onboarding does not proceed and the existing contract is left unchanged. | Must | User chose: warn and let the user choose whether to replace it. |
| FR-62 | Review applies to code-producing deliveries and onboarding | The code review step runs for new service, API change and bugfix deliveries and for onboarding, and does not run for documentation-only deliveries. | Must | Replaces FR-26: user confirmed onboarding is included in code review. |
| FR-63 | Agent asks the user to confirm a bug in the existing code | When a coding agent considers that a failing contract test during onboarding reveals a bug in the existing code, it asks the user in the onboarding's progress, like other agent questions, and changes the code only after the user confirms; until answered, it waits. | Must | User chose: the coding agent asks in the progress and waits for the answer. |
| FR-64 | Mentions on onboarding pull requests | Mentions of the GitHub App on a pull request opened for an onboarding (fix requests and clarifications) are handled the same way as mentions on delivery pull requests. | Must | User chose: the same as for delivery pull requests. |
| FR-65 | Onboarding verification and progress like a delivery | Onboarding's verification works like a delivery's: test repair rounds and review rounds are each capped at 5, its progress is shown, its agents' questions can be answered and a failed stage can be retried. | Must | User chose: exactly like a delivery. |
| FR-66 | List and reopen onboardings | Signed-in users can list onboardings and reopen any of them to see its state and progress, in the same way as requirements sessions. | Must | User chose: listed and reopened like sessions. |
| FR-67 | Onboarding tab in the web client | The web client has its own Onboarding tab in the top navigation, where a signed-in user picks a repository and branch and starts an onboarding. | Must | User chose both a dedicated tab and an entry point from the repository picker. |
| FR-68 | Start onboarding from the repository picker | The repository picker in the Requirements tab offers an action that starts an onboarding of the selected repository and branch and opens it in the Onboarding tab. | Must | User chose both a dedicated tab and an entry point from the repository picker. |
| FR-69 | Reopen onboardings from the Workflows list | The Workflows page offers an Onboarding filter for OnboardingWorkflow executions, and each onboarding execution in the list links to its page in the Onboarding tab, where its state and progress are shown. | Must | User chose to reuse the Workflows list filtered to onboarding workflows to satisfy FR-66. |
| FR-70 | Onboarding UI covers every backend action | The Onboarding page lets the user do everything the /onboarding/sessions endpoints offer: send messages and answer the interviewer's questions, decide whether to replace an existing contract, update the checkout, finalize, fork after a message, retry a failed turn, follow the delivery progress, answer agent questions (including the confirmation of a bug in the existing code), accept open review findings or give instructions about them, and retry a failed stage. | Must | User chose: everything the backend offers. |
| FR-71 | Repository and branch in GET /workflows | Each OnboardingWorkflow, RequirementsWorkflow, ApiDesignWorkflow and DeliveryWorkflow execution returned by GET /workflows includes the repository and branch it works in, and the Workflows page shows them. | Must | User chose to return repository and branch for onboarding, requirements, API design and delivery workflows. |
| FR-72 | Onboarding's child workflows link to its page | In the Workflows list, every DeliveryWorkflow and CodegenWorkflow execution started for an onboarding links to that onboarding's page in the Onboarding tab. | Must | User chose to link an onboarding's delivery and code generation workflows to the onboarding's page. |
| FR-73 | Onboarding ID in GET /workflows | Every execution returned by GET /workflows that was started for an onboarding (the OnboardingWorkflow itself and its DeliveryWorkflow and CodegenWorkflow executions) includes the ID of that onboarding, which the Workflows page uses to link to the onboarding's page. | Must | User chose to have the API return an onboarding ID rather than have the page follow parent_workflow_id. |
| FR-74 | Inapplicable new fields are null | Every execution returned by GET /workflows includes the new repository, branch and onboarding ID fields, and each one is null when it does not apply to that execution (for example, repository and branch of a chat or sample workflow, or the onboarding ID of a run not started for an onboarding). | Must | User chose to always return the fields, with null when they do not apply. |
| FR-75 | One page for every flow | The web client shows every flow on one Flows page instead of separate Chat, Requirements, API design, Onboarding and Workflows tabs. The page lists the top-level flows; opening one lists its child flows and steps with their statuses, highlights each one waiting for the user (unanswered questions, a coding agent's questions, open review findings or a contract decision) with a button that opens its questions, and opens a flow's conversation, session or onboarding in a panel on the same page. New chats, requirements interviews and onboardings are started from that page. | Must | User asked to see each flow on the same page rather than on a page per kind of flow. |
| FR-76 | List top-level flows and a flow's children | GET /workflows takes top_level=true to list only executions without a parent (a session's delivery, even one started again on its own, is never top-level), and parent=<workflow_id> to list only the children of that execution together with the session's delivery runs. They combine with the other filters; parent with top_level, or an empty or malformed parent, answers 422. | Must | The Flows page lists top-level flows and expands one into its children. |

## Non-functional requirements

| ID | Requirement | Description | Priority | Rationale |
| --- | --- | --- | --- | --- |
| NFR-1 | Limit sign-in attempts | Sign-in and registration attempts are limited per client address per minute (AUTH_LOGIN_ATTEMPTS_PER_MINUTE, default 10); further attempts answer 429 with Retry-After. | Must |  |
| NFR-2 | Never echo secrets | Passwords, private keys and tokens are never part of a response or a validation error. Passwords are stored as salted scrypt hashes and the GitHub App key is stored encrypted. | Must |  |
| NFR-3 | Expiring sessions | Session tokens are HS256 JWTs signed with AUTH_JWT_SECRET (at least 32 characters) that expire after AUTH_TOKEN_TTL_HOURS, 12 by default. Without a usable secret, sign-in and authenticated endpoints answer 503. | Must |  |
| NFR-4 | Report unavailable dependencies | When Temporal answers a request with an error or the request storage cannot be reached, an endpoint answers 503 with a detail saying which. | Must |  |
| NFR-5 | Bound request sizes | Messages and tasks have at most 10000 characters, an attachment at most 20 MiB and GitHub configuration input at most 16 KiB; larger input answers 413 or 422. | Must |  |
| NFR-6 | Validation errors | Malformed input answers 422 with a detail; an unknown session or request ID answers 404; an action the session's state does not allow answers 409. | Must |  |
| NFR-7 | GET /workflows only gains fields | GET /workflows keeps its existing fields (workflow_id, run_id, workflow_type, status, task_queue, parent_workflow_id, start_time, close_time, next_page_token) with their current names and meaning; the change only adds fields. | Must | User: only add fields. |

## Technical requirements

| ID | Requirement | Description | Priority | Rationale |
| --- | --- | --- | --- | --- |
| TR-1 | Stack | The backend is a Python 3.12 FastAPI application with Temporal workflows and PostgreSQL storage, in backend/. The web client is a React application in frontend/. | Must |  |
| TR-2 | Isolated coding agents | Coding agents run in Docker containers built by the workers, without access to Temporal, the database or Docker. | Must |  |
| TR-3 | Verifiable service image | The Dockerfile at the repository root builds the API as a self-contained service with its own PostgreSQL database, served on port 8080 by a non-root user, so that contract tests can run against it alone. | Must |  |
| TR-5 | Pull request permission and comment webhook in the app manifest | The GitHub App manifest this instance offers requests the pull_requests: write permission in addition to its existing permissions, turns on the webhook pointing at POST /connectors/github/events, and subscribes to pull request conversation comment and inline review comment events; the webhook secret GitHub returns with the created app is stored encrypted with the connection. | Must | Replaces TR-4: mentions arrive through the app's webhook. |
